#+title: myweb

Author, build and deploy my web sites from a datalad dataset of org sources
(~~/keep/web~).  See [[file:proposal.md]] and [[file:decisions.md]] for the
design.

* Site layout

#+begin_example
~/keep/web/
  myweb.toml              taxa and targets, travels with the dataset
  config/_default/        hugo config common to all targets
  config/<environment>/   per target hugo config (baseURL, ...)
  archetypes/<taxon>.org  templates for "myweb new" ($title, $date, $slug, ...)
  themes/plain/           the theme, plain HTML, no JavaScript
  content/<taxon>/<slug>/ one item, a Hugo leaf bundle:
      <slug>.org            source, for taxa rendered by ox-hugo
      index.md              exported by ox-hugo, committed
      index.org             source, for taxa rendered by hugo (notes)
      version.txt           version stamp, see "myweb version"
      *.svg, *.png, ...     resources, linked relatively
#+end_example

Item metadata is in org keywords: ~#+title~, ~#+date~, ~#+hugo_tags~ (or
~#+tags[]~), ~#+hugo_draft~ (or ~#+draft~), and:

- ~#+audience:~ personal | work | both :: which targets get the item
- ~#+visibility:~ public | unlisted | protected :: unlisted and protected
  items are built but never listed (indices, RSS, sitemap) and carry
  ~noindex~.  Protected items get an ~.htaccess~ and only go to targets with
  ~auth = true~.

Hugo can not filter on front matter so myweb writes an extra hugo config
per build: content mount exclusions and cascades by path.

Every headline gets a ~CUSTOM_ID~ property, a slug of its heading
(~myweb ids~, and ~publish~ does it too).  Org's generated ~org1234abc~
ids are replaced, others kept.  The id is the section's HTML anchor and
the theme puts a ~#~ link to it after each heading.

Each page's org source, less ~:noexport:~ and ~COMMENT~ subtrees, is
published beside it as ~<slug>.org~ and the theme links it ("org source",
from the ~source~ param myweb cascades).  A top ~.htaccess~ serves ~.org~
as the target's ~org_type~ (default ~text/plain; charset=utf-8~, needs
~AllowOverride FileInfo~; set ~org_type = ""~ to omit it).

* Search and access realms

Site search runs in the reader's browser over static JSON indexes that
~myweb build~ (and ~deploy~) writes after hugo, so a reader can search exactly what the
web server lets them fetch.  There is no server side to trust.

Every page is in one access realm: ~public~, or for a protected page the
realm its ~#+access:~ names (default ~protected~) from the target's
~realms~, each an Apache ~Require~:

#+begin_src toml
[target.work.realms]
protected = "valid-user"       # the default when none are given
dune = "user alice bob"        # eg a collaboration's talks
#+end_src

A page whose realm the target lacks is not built for it.  One function
(~access.htaccess~) writes the ~.htaccess~ for both a realm's pages and its
index, so they always admit the same readers, and all use ~AuthName~ = the
realm so one login covers the realm.

- ~search/index.json~ :: public pages only
- ~search/<realm>/~ :: the realm's ~.htaccess~, its ~index.json~, and a copy
  of the search page that loads the public and the realm's index
- unlisted pages :: in no index

No index holds two realms, so a reader of ~dune~ learns nothing of
~protected~ and vice versa; one with both searches each.  The build fails
if any index holds a page of another realm or a realm index is not guarded
like its pages.  The public search page links each realm's search, so
realm names are public.  Unlisted and protected pages were already kept
out of lists, RSS and the sitemap.

Without JavaScript the search page offers the section indices instead.

* Talks migration

~myweb talks~ migrates the old ~~/sync/talks~ (only ever read) into the
~~/keep/talks~ dataset as ~<group>/<YYYY>/<MM>/<DD>/<topic>/~ with a
~talk.json~ per talk.  Set ~[talks] source~ and ~dest~ to change them.

#+begin_example
myweb talks scan        # find new/changed talks, write digests of those needing review
myweb talks todo -p     # digests still needing a review
myweb talks fields      # what a review holds
myweb talks migrate [--redo] [-n] [--save]
myweb talks report      # rewrite MIGRATION.org
#+end_example

A candidate is a slide source (org or LaTeX beamer, LibreOffice,
PowerPoint) or a slide-like PDF (5+ landscape pages not from a plotting
tool).  Its date comes from the path or file name, then ~#+date~ /
~\date{}~, then the PDF's CreationDate, then the file's mtime (birth times
are those of a later copy).  A partial path date (no day) is completed by
the first fallback agreeing with it.  Duplicates (same PDF, or same group,
date and name) are migrated once, preferring the date tree.

A review (~migration/reviews/<id>.json~), written by reading the
candidate's digest (by a person or an LLM), says if it is a talk and gives
title, venue, summary and problems.  Problems block migration and are
listed in ~MIGRATION.org~ for a person to decide.  A changed source makes
its review stale.  State is ~migration/inventory.json~.

* Talks on the web

Every ~talk.json~ in the talks dataset is a page at
~talks/<group>/<YYYY>/<MM>/<DD>/<topic>/~ with its summary, venue, authors
and PDF; nothing is generated into the site dataset.  Each build writes
the talks a target gets to the cache and mounts them as ~content/talks~,
so a newly migrated talk appears on the next ~myweb deploy~.

- taxonomies :: ~groups~, ~topics~ (topic and series), ~tags~ (keywords)
- ~/talks/~ :: all listed talks by year, with a fuzzy filter and group and
  topic selections (~?q=&group=&topic=~) when JavaScript runs
- search :: talks are in the per-realm search indexes with their facets

Access: a talk's ~audience~, ~visibility~ and ~access~ come from its
~talk.json~, else ~[talks]~ in ~myweb.toml~ (per group in
~[talks.group.<name>]~), and are handled as for articles.  ~migrate
--redo~ keeps them.

Resolving ~MIGRATION.org~:

#+begin_example
myweb talks resolve <id> --accept [-m why] [-d YYYY-MM-DD] [-t topic]
myweb talks resolve <id> --reject [-m why]
myweb deploy local
#+end_example

* Deploying

~myweb build <target>~ builds a target to its stage
(~~/.cache/myweb/stage/<target>~) and checks it.  ~myweb deploy
<target>...~ (or ~--all~ for ~publish_targets~) builds and then sends the
stage by each method the target sets, in this order:

- ~dest~ :: a local directory, by ~rsync --delete~ (eg ~~/public_html~)
- ~rsync~ :: a ~host:path/~, from ~dest~ if set, else from the stage
- ~git~ :: a repository URL; its ~branch~ (default ~gh-pages~) gets the
  stage as one new commit, pushed.  A plain git work tree in
  ~~/.cache/myweb/deploy/<target>~ follows the remote branch.

Paths in ~keep~ (default ~drop/~) are never deleted at any destination.
A server that admits only some file types (eg hierocles, only ~.html~)
needs ~allow_files = true~: the top ~.htaccess~ then grants, by
~FilesMatch~, every file type in the build.  Because ~Files~ sections
merge after directories, every protected ~.htaccess~ repeats its
~Require~ in a ~FilesMatch~ so the grant can not open protected files.
Extra ~files~ are written at the top of the build.

The built stage holds plain files, talk PDFs copied out of the annex, so
no destination needs git-annex or datalad.  Which items a target gets is
the item's ~#+audience:~ (and a talk's): ~personal~ goes only to targets
serving personal, ~work~ only to work, ~both~ to each.  ~talks = false~
keeps every talk off a target.  A theme menu entry whose page was not
built is left out.

The site's ~myweb.toml~ says what each target gets; the host's
~config.toml~ says where it goes from this host:

#+begin_src toml
[target.github]                 # myweb.toml
audience = ["personal", "both"]
auth = false                    # GitHub Pages reads no .htaccess
talks = false
org_type = ""
keep = []
branch = "master"
[target.github.files]
".nojekyll" = ""                # no Jekyll pass over the built site

[target.github]                 # ~/.config/myweb/config.toml
git = "git@github.com:brettviren/brettviren.github.io.git"
[target.work]
rsync = "hierocles:public_html/"
#+end_src

* Commands

#+begin_example
myweb new posts "A Title" -t tag -d 2026-12-31   # draft, TODO in org-agenda
myweb new notes "TIL" -m "One-liner note."
myweb edit <item>       # Emacs + background "hugo server" with drafts + browser
myweb status [-a]       # drafts: deadline, TODO, words, figures, ...
myweb export [<item>]   # ox-hugo export of stale items
myweb ids <item>|-a [-n] [--commit]  # slug CUSTOM_ID for every headline
myweb check <item>      # export, build to a check stage, link check; .check.txt
myweb publish <item>    # undraft, export, save, stamp, tag, build, deploy
myweb build [target]    # build to stage, .htaccess, search, verify
myweb deploy <target>...|-a  # build, then to dest, rsync and/or git push
myweb version [-u]      # show/update version.txt stamps
myweb search ...        # passes to the configured search (orgface search)
myweb setup systemd|cron|git [-T target] [--print]
#+end_example

* Version stamps

A ~version.txt~ holds ~git describe~ of the last commit that touched what it
covers, plus the commit hash.  All ~version.txt~ files are excluded from what
any stamp covers, so committing stamps does not change them: a stamp changes
iff its content does.  ~publish~ commits content, then stamps, then commits
the stamps.

* Configuration

~~/.config/myweb/config.toml~ holds host specifics (site path, hugo and
Emacs commands) and may override any ~[taxon.X]~ or ~[target.X]~ field of the
site's ~myweb.toml~.  ~MYWEB_SITE~, ~MYWEB_HUGO~ and ~MYWEB_CONFIG~ override.

Load ~src/myweb/myweb.el~ in Emacs so interactive ox-hugo exports (eg
~org-hugo-auto-export-mode~) keep bundle links relative, as ~myweb export~
does.  ~myweb edit~ loads it for you.
